How This Blog Is Built

The full stack behind this site: plain HTML, Tailwind CSS from a CDN, and GitHub Pages. No build step, no framework, no config files. Here is why that was the right call.

The stack at a glance

Layer Choice Why
Hosting GitHub Pages Free, zero ops, auto-deploys on push to main
CSS Tailwind CSS CDN No build step; utility classes directly in HTML
Fonts Google Fonts (Inter) One <link> tag, no local assets
JavaScript None (Tailwind config inline only) No interactivity needed
Build None Files are served exactly as committed
CI/CD GitHub Pages default Auto-deploy on push, no workflow file required

Why no framework

A personal portfolio has maybe six pages and changes a few times a year. The overhead of a bundler, a dependency tree, a build command, and a deploy workflow exists to solve problems this site does not have.

Plain HTML with Tailwind CDN means:

  • Open any file in a browser directly from disk. No server needed to preview.
  • Edit a line, commit, push. The site is live in under a minute.
  • Zero supply chain surface. No node_modules, no lockfile drift, no CVEs in dev dependencies.
  • The file you read is the file the browser receives. No source maps, no transpilation.

The tradeoff is duplication. The nav and footer are copy-pasted into every page. For six pages, that is a manageable cost.

Tailwind CSS via CDN

Tailwind ships a CDN script that generates styles from utility classes at runtime. It is not the production build path (that would require PostCSS and tree-shaking), but for a low-traffic personal site with a handful of pages, the performance difference does not matter.

The benefit is everything Tailwind offers: a consistent design system, dark-mode utilities, responsive prefixes, and hover states, all without a config file or build step.

GitHub Pages

Push to main. Done. GitHub Pages serves the repo as a static site under nitrocode.github.io. No Nginx config, no deployment pipeline, no DNS management beyond the default. The opentofu/ directory even serves as a live static API emulation (see the OpenTofu registry post).

File structure

Each page lives at its URL path with an index.html file: 

nitrocode.github.io/
├── index.html              # /
├── about/index.html        # /about/
├── blog/index.html         # /blog/
├── blog/opentofu-registry/ # /blog/opentofu-registry/
│   └── index.html
├── blog/how-this-blog-is-built/
│   └── index.html          # this page
├── projects/index.html     # /projects/
├── resume/index.html       # /resume/
└── opentofu/               # static registry emulation

No routing config. GitHub Pages serves index.html for any directory URL by default.

The next step: Markdown + Jekyll

The current setup works well for pages that rarely change. Blog posts are different. Writing HTML by hand for prose content is friction. The right path is to separate content from structure.

The planned migration:

  1. Add _config.yml to enable Jekyll on GitHub Pages.
  2. Move blog post content to .md files with YAML front matter.
  3. Create _layouts/post.html using the existing Tailwind prose styles.
  4. Use Jekyll's site.posts loop to auto-generate the blog index.
  5. Move nav and footer to _includes/ to eliminate the copy-paste.

GitHub Pages runs Jekyll natively, so no CI workflow is needed. Write a markdown file, push, and the page appears. The design stays identical; only the authoring workflow changes.

Lessons

  • Match the tool to the problem. Six pages updated a few times a year do not justify a framework.
  • Static is underrated. No server, no database, no ops. A directory of files is a surprisingly capable publishing platform.
  • The CDN build of Tailwind is fine here. The tradeoff against a full PostCSS pipeline is worth it when there is no build step to integrate with.
